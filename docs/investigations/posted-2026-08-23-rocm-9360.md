I went looking at this because it changes behaviour for every device, and I have RDNA2/3/3.5/4 hardware to test on. Sharing what I measured, because I could not reproduce the motivating failure and I think the underlying blocker may be a different one — which would change what the right fix is.

All numbers below are ROCm 7.14.0, DRM 3.64.0, on gfx1201 (Radeon AI PRO R9700), gfx1100 (RX 7900 XTX), gfx1151 (Radeon 8060S), gfx1030 (RX 6950 XT). All four report minimum 4096 B / recommended 2097152 B.

## I could not reproduce kernel faults at 4 KiB boundaries

The stated motivation is that "GPU kernels accessing VMM-mapped memory at 4 KB-aligned boundaries trigger illegal memory access faults". Since that is a claim about kernel access rather than about an API return, I tested it with a kernel.

The test builds a contiguous span from N minimum-granularity handles — one 4 KiB physical handle per page, mapped back to back — so **every page boundary in the span is also a physical-handle boundary**. Then three access shapes, each verified by exact host readback with `hipDeviceSynchronize` checked after every launch:

- **A.** every 32-bit word across the whole span, so every boundary is touched
- **B.** only the words immediately either side of each boundary
- **C.** 8-byte stores deliberately **straddling** each boundary, so a single access has its bytes in two different physical handles

On gfx1201, 512 handles / 511 boundaries:

```
=== AMD Radeon AI PRO R9700 (gfx1201) ===
minimum granularity 4096 B | recommended 2097152 B
building a contiguous span from 512 handles of 4096 B each = 2048 KiB

mapped 512 handles and set access over the whole span: ok
arm A  every word across 511 handle boundaries: launch no error | sync no error | mismatches 0
arm B  words on both sides of each boundary:       launch no error | sync no error | mismatches 0
arm C  8B stores STRADDLING each boundary:         launch no error | sync no error | mismatches 0
```

Identical clean result on gfx1100, gfx1151 and gfx1030. Arm C is the case I expected to fault if adjacent minimum-granularity handles were not stitched together correctly in the page tables, and it passes.

This does not prove you saw nothing — the shape of your failing access may differ from all three of mine. Could you share the access pattern or a reproducer? I'm happy to run it across all four architectures.

## The constraint I do find is a whole-handle rule, not an alignment rule

Sweeping handle sizes against mapping offsets, `hipMemSetAccess` succeeds iff the range covers a whole number of **complete mapped handles** — it must begin and end on handle boundaries. This is alignment *relative to where handles were mapped*, not absolute alignment of the address. A single 2 MiB handle mapped at `base + 4 KiB`, which is not 2 MiB aligned, is accepted at full-handle length:

```
---- handle size 2M ----
offset     off/min        hipMemMap        SetAccess(len=hs) SetAccess(len=min)
0          0 x min        ok               ok               invalid-value
4K         1 x min        ok               ok               invalid-value
8K         2 x min        ok               ok               invalid-value
64K        16 x min       ok               ok               invalid-value
1M         256 x min      ok               ok               invalid-value
2M         512 x min      ok               ok               invalid-value
```

Every offset is accepted at full-handle length; every one is rejected at a sub-handle length. With 4 KiB handles the same sweep accepts 4 KiB lengths at every offset. The distinction matters here because only an *absolute*-alignment requirement would argue for raising the reported minimum — a whole-handle rule is unaffected by what `MINIMUM` reports.

## What I suspect the real blocker is: descriptor exhaustion

While running the above I hit this, and I think it may be the actual reason VMM looks unusable at minimum granularity:

```
building a contiguous span from 1024 handles of 4096 B each = 4096 KiB
FATAL hipMemCreate(&h, gmin, &prop, 0) -> out of memory (2)
```

`hipMemCreate` consumes **one dmabuf file descriptor per handle** — `readlink` on the new fd shows a `/dmabuf:` target, and `hipMalloc` consumes none. At the stock soft `RLIMIT_NOFILE` of 1024 that caps a process at **1015 handles**, on all four architectures, independent of VRAM. The failure surfaces as `hipErrorOutOfMemory`.

So a consumer that queries `MINIMUM` and builds a pool from 4 KiB handles runs out of descriptors at roughly **4 MiB** of VMM — while the card reports tens of GiB free. That would look exactly like "VMM-based memory management is blocked on RDNA4", and it is not arch-specific.

If that is the mechanism, then this PR does fix the symptom, by making each descriptor cover 512× more memory: 1015 × 2 MiB ≈ 1.98 GiB instead of 1015 × 4 KiB ≈ 4 MiB. But it fixes it by removing the fine-grained mapping capability that does work, and 1.98 GiB is still well short of the device. Addressing the descriptor cost directly would remove the ceiling without giving up granularity. I'm filing that separately with the full measurements rather than derailing this PR, and will cross-link it.

## Narrower concerns with the patch as written

1. **It overrides `MINIMUM`, not just `RECOMMENDED`.** The `if (!useHostDevice)` block runs after the min/recommended selection, so `hipMemAllocationGranularityMinimum` now returns 2 MiB. Callers who deliberately query the minimum to do fine-grained mapping — which works, per the tests above — lose that. If the intent is "prefer 2 MiB", raising `RECOMMENDED` communicates it without redefining the floor.
2. **The scope is every non-host device, but the motivation is gfx1201.** As written this changes gfx906, gfx942, gfx950, gfx1030, gfx1100 and everything else. The added test is named `_RDNA4`, so the test scope and the code scope don't match.
3. **`HIP_VMM_GRANULARITY` is unvalidated.** `strtoul` with only a `val > 0` check will accept a non-power-of-two or sub-page value and hand it back as the granularity. A rejection or round-up for values that aren't a multiple of the true device page size would prevent a confusing downstream failure.

Reproducers for everything above are standalone HIP files with no framework dependency, and I can share them or test any candidate patch on all four architectures.
