I can narrow this one down to a single instruction, with a reproducer that
needs only ROCm.

**Setup.** hipEngine's `hip_dot_path.hip` q8 row exactly as filed (n=32768,
body_iters=64, 16 groups, block 64, 128 MiB per buffer, 256 MiB streamed per
dispatch), ROCm 10.0.0 (AMD clang 23.0.0git), Radeon 8060S / gfx1151, with an
RX 7900 XTX / gfx1100 as the dGPU control. All timings are hipEvent medians
over 20 chained launches, 3 warmups, 7 samples, 3 repeats, every arm checked
against a CPU oracle; bandwidth is 256 MiB / time.

**1. It is codegen, not HIP.** I took the RADV/ACO ISA for the same shader
(Mesa 26.0.3) and packaged it into an ordinary HSACO — inline asm with pinned
register constraints, LLVM emitting the kernarg prologue and descriptor —
so the ACO body runs under HIP dispatch on the same `hipMalloc` buffers as
the LLVM kernel, in one process:

| gfx1151, HIP dispatch | median | bandwidth |
| --- | ---: | ---: |
| LLVM kernel (per-element `global_load_b32`, as in the issue) | 3534 us | 76 GB/s |
| ACO body, wave64, same dispatch and buffers | 1142 us | 235 GB/s |
| ACO body, wave32 | 1238 us | 217 GB/s |
| Vulkan, RADV, original shader | 1118 us | 240 GB/s |

240 GB/s is DRAM peak on this part. So the 3.2x is in the instruction
stream, not in the runtime or memory placement.

**2. The instruction streams differ in one respect.** Both compilers emit
32 `global_load_b32` per iteration with 64-bit VGPR-pair addressing, the same
`v_dot4_i32_iu8` count, and the same consume tail (`s_waitcnt vmcnt(30)` dot,
`vmcnt(28)` dot, ... `vmcnt(0)` dot). ACO hoists the address arithmetic and
issues the loads back-to-back inside `s_clause` (runs of 18/10/4). LLVM
interleaves 2-4 address VALU ops between every 1-3 loads and emits no clause
over them. None of `-misched=gcn-max-memory-clause` (with or without
`-amdgpu-max-memory-clause=32`), `gcn-max-ilp`, or `gcn-iterative-ilp` changes
that: the loads stay interleaved and the time stays at 3530-3657 us.

**3. Surgery on LLVM's own assembly.** From the `--save-temps` `.s` of the
LLVM kernel, reassembled unchanged (A) and with mechanical edits:

| arm (gfx1151) | change vs A | median | bandwidth |
| --- | --- | ---: | ---: |
| A control | none | 3534 us | 76 GB/s |
| B | address VALU hoisted, 32 loads back-to-back, `s_clause 0x1f` (96 VGPRs) | **1276 us** | 210 GB/s |
| C | identical to B minus the single `s_clause 0x1f` line | 3244 us | 83 GB/s |
| D | LLVM's original order, `s_clause` over each existing 1-3 load run | 3213 us | 84 GB/s |

B and C differ by one instruction and by 2.54x. Grouping without the clause
(C) is worth 9%; clausing LLVM's existing short runs (D) is worth 10%; the
clause over the full burst is worth 2.8x. On gfx1100 the same four arms are
331 / 309 / 307 / 329 us — grouping helps ~7% and the clause is irrelevant,
which is why the issue's gfx1100 numbers look fine.

**What this suggests.** On gfx1151 a hard clause over a long burst of
same-cacheline VMEM loads matters a great deal; LLVM's scheduler does not
produce the burst, so `SIInsertHardClauses` has nothing to wrap. The 96-VGPR
budget the hoist needs still leaves wave32 at the 16-wave occupancy cap on
gfx11, so this does not look like a pressure/occupancy trade-off. I have not
attempted a patch; a scheduler mutation that clusters VMEM loads to the same
base across the unrolled body, or a gfx115x-specific tuning of the
max-memory-clause strategy, seems like the place to look.
