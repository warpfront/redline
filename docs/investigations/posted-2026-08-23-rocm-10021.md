Confirming this on **gfx1201** (Radeon AI PRO R9700), stock **ROCm 7.14.0**, DRM 3.64.0 — the original report is gfx1100, so the defect reproduces on RDNA4 as well.

The reproducer is a single self-contained HIP file, no framework: capture a 512-node graph, instantiate it, launch and sync it once to establish a clean baseline, then exhaust device memory with descending `hipMalloc` chunks and call `hipGraphExecUpdate` on the exec repeatedly.

It fails fast on purpose. Every fallible call — begin-capture, the in-capture launch's `hipGetLastError`, end-capture, instantiate, the update itself, the post-update launch, the sync, graph destroy — aborts immediately and names the round and the call. Nothing is accumulated and ignored, so a crash cannot be attributed to an earlier swallowed error.

**Deterministic: 6/6, always round 4, exit 139.** Three runs with launches between updates, and three with a `--update-only` switch that performs no launches at all between updates. That distinction matters because with no launches in between, a poisoned-stream explanation is excluded — the fault is reached by `hipGraphExecUpdate` alone.

The faulting frame is five stack levels below `hipGraphExecUpdate`, with no application frame in between, and **`rdi` is `0x0` at the faulting instruction**. That is consistent with the null-kernarg path #10022 addresses — `getGraphKernArg()` returning null under kernarg-pool exhaustion and the result being used without a check — though with a stripped release build I can't name the exact callee, so I'd treat the register as corroborating rather than proving.

The first three updates returning `result=0` with `bad_node=(nil)` and the fourth faulting is consistent with pool growth failing on a later grow attempt, but this run does not identify which attempt.

Two notes that may be useful for prioritising #10022:

- The reproducer needs no framework and no unusual configuration — an out-of-memory condition plus `hipGraphExecUpdate` is sufficient. Anything that updates a graph exec on a full device can hit this.
- `hipGraphExecUpdate` is on the decode path of real inference stacks. llama.cpp builds with `GGML_HIP_GRAPHS` on by default and calls the CUDA-equivalent per token, and a full device is the normal operating point for KV-cache-heavy serving, not an edge case. The failure mode is a runtime segfault an application cannot defend against, since the update returned success the previous three times.
