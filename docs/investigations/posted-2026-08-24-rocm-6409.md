Following up with a reproducer that needs **nothing but a stock ROCm install** — no third-party runtime, no PM4, no Vulkan, and no profiler. On the Discord thread the answer was that the team was checking whether this had been reproduced internally, so the goal here is to remove every dependency that could be in the way of that.

All numbers below are **ROCm 7.14.0**, Ubuntu 26.04, measured 2026-08-23.

## The reproducer

One file. The kernel is a single workitem doing one `atomicAdd`, so what it measures is submission and completion cost rather than compute.

```
hipcc --offload-arch=$(rocminfo | awk '/gfx/{print $2; exit}') -O3 aql_dispatch_floor.cpp -o adf
./adf
```

Three arms: `N` launches on one stream with a single sync at the end; `N` launches each with its own sync; and the same `N` launches captured once into a `hipGraph` and replayed.

Two things are deliberate, both because of points raised earlier in this thread:

- **No profiler.** `rocprofv3` was reported here as not tracking dispatch times usefully. Timing is a host `steady_clock` span and a `hipEvent` span over the *same* batch, printed side by side; if they disagree by more than 25% the row prints `DIVERGE`. Every run below printed `agree`.
- **Correctness-gated.** The atomic counter must equal exactly `N × replays`, or the row prints `COUNTER MISMATCH` and the timing is declared invalid. An arm cannot look fast by not doing the work.

## Per-dispatch cost, median of 200 replays after 20 warmups (µs)

| GPU | arch | per-launch-sync | stream-loop | graph-replay | graph vs loop |
| --- | --- | ---: | ---: | ---: | ---: |
| Radeon AI PRO R9700 | gfx1201 | 18.477 | 2.530 | **2.149** | 1.18× |
| RX 7900 XTX | gfx1100 | 19.447 | 3.152 | **2.826** | 1.12× |
| Radeon 8060S (Strix Halo) | gfx1151 | 7.015 | 1.839 | **1.747** | 1.05× |

The gfx1201 sweep over `N`, showing where the floor settles:

| N | stream-loop | per-launch-sync | graph-replay |
| ---: | ---: | ---: | ---: |
| 1 | 22.880 | 22.659 | 28.733 |
| 8 | 4.987 | 19.124 | 6.743 |
| 64 | 2.824 | 18.648 | 2.528 |
| 256 | 2.600 | 18.529 | 2.200 |
| 512 | 2.530 | 18.477 | 2.149 |

Three observations:

1. **`hipGraph` removes 5–18% of per-dispatch cost, not an order of magnitude** — and at small `N` it is *slower* than a plain launch loop, because instantiate and launch setup are not amortised yet.
2. **A per-dispatch sync costs ~18.5 µs** on the discrete parts and ~7 µs on the APU.
3. **The floor has not moved since ROCm 7.2.** Measuring real `hipGraphLaunch` on the same GPU model on 7.2 gave 2.113–2.133 µs/dispatch. It is 2.149 µs on 7.14.

## The graph API already batches, and it is still this expensive

This is the part I think matters most for triage, because it forecloses the obvious reading that this is just a missing batching optimisation.

Reading `projects/clr/hipamd/src/hip_graph_internal.cpp` on `release/therock-7.14`: graph launch already pre-captures AQL packets and dispatches them as a batch — `CaptureAQLPackets()`, a flat buffer that "append[s] one 64-byte AQL packet" at a time, and `dispatchAqlPacketBatchFlat(...)`, which is taken whenever captured packets exist. So the 2.149 µs above is measured **with** AQL packet batching active.

For reference on what the same work costs when it is lowered to a single retained PM4 indirect buffer instead of N AQL packets, on the same host, same GPU, same ROCm build, same no-op kernel:

| path | N=256 | N=512 |
| --- | ---: | ---: |
| `hipGraph` replay (standalone reproducer above) | 2.200 | 2.149 |
| one retained PM4 IB, conservative / dependency-preserving | 0.1759 | 0.1436 |
| **ratio** | **12.5×** | **15.0×** |

Measurement bases differ and the difference does not favour the PM4 row: the AQL rows are GPU-timestamped dispatch spans, the PM4 rows are end-to-end host latency per replay, so they *include* host submission cost.

One cross-check worth stating, because it is the claim most worth attacking. The standalone HIP harness measures `hipGraph` replay at **2.149 µs**. A separate implementation that models an agent-scope fence policy — different language, no shared code with the harness — lands at **2.0948 µs**. That is 2.6% apart, and `hipGraph` uses agent-scope fencing, so the two independent routes agree on what the API actually does.

## An unrelated finding that may be useful to engine authors today

Same kernel, same node count, only the declared dependency edges differ, built with `hipGraphAddKernelNode` so the edges are exactly as stated (gfx1201, N=512, µs/dispatch):

| graph shape | cost |
| --- | ---: |
| chain (node *i* depends on *i−1*) | 2.163 |
| independent (no edges) | 6.432 |
| fanout-join | 7.055 |

Declaring nodes **independent** is ~3× *more* expensive per dispatch than a strict serial chain. The cheapest shape is the fully ordered one. I have not established the mechanism — this measures cost as a function of declared structure and does not inspect emitted packets — but it means a decode step expressed as a parallel or fanout graph pays roughly 3× the submission cost of the same work expressed as a chain, which is actionable without any runtime change.

## What this implies for decode, as arithmetic

A dense 61-layer decode step issues order 450–550 dispatches per token. At the measured 2.149 µs floor that is ~1.0–1.2 ms per token of pure submission cost; a 70 tok/s decode is 14.3 ms per token, so submission is order 7–8% of the step.

Two independent end-to-end results in this thread bracket that: @lhl measured **+8.13%** decode on a W7900, and a llama.cpp maintainer measured **62 → 68.5 tok/s (+10.5%)** on an MoE. A floor microbenchmark and two real engines agreeing on magnitude is the strongest statement available here.

## The narrow version of the request

The ask earlier in this thread was for "a documented way of running low-level dispatches with HIP." Stated smaller and more implementable, the properties that produce the difference above are:

1. **One submission for many dispatches.** Already partly present — graphs batch AQL packets today.
2. **Fences where the data flow requires them, rather than per dispatch.** Still AQL, no new submission path: a dependency-preserving policy that only drops redundant fences measures 1.288 µs/dispatch versus 2.149, i.e. 1.67× at the floor, while keeping dependency order. A documented per-graph or per-launch fence-scope hint would let a consumer opt into this where it already knows the dependency structure — which is exactly what a graph is.
3. **A statement about what kernel state persists across dispatches within a single submission,** per architecture. This one is a documentation question rather than new work: consumers cannot rely on it today because it is unspecified, not because it does not hold.

(2) looks like the cheapest of the three to expose and it is worth 1.67× on its own.
